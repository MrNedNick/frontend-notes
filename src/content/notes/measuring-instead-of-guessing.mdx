The <a href={sitePath('/stacks/')}>stack comparison</a> puts a number next to each framework. Numbers
like that are usually quoted from a blog post about a different app, on a
different machine, in a different year. These were produced on one laptop,
using the same script and the same method every time — see the stacks page
for exactly when each row was measured.

## What is measured

**Cold build time.** Delete every cache the tool keeps — `dist`, `.astro`,
`.svelte-kit`, `.angular`, `node_modules/.vite` — then time `npm run build`.
Installing dependencies is not counted; that is a network measurement, not a
build one.

**JavaScript on first load.** Serve the production build over a local HTTP
server, open the page in headless Chrome through the DevTools protocol, and sum
`encodedDataLength` for every response whose MIME type is JavaScript, six
seconds after navigation, so lazily loaded chunks and the first data round trip
are included.

## What the numbers do not say

They compare five different applications, not five builds of one. A dashboard
with a virtualized ten-thousand-row table is not the same amount of product as a
week-grid booking form, and neither is a component library build.

Two of them also ship an in-browser mock API, because they have no backend:
93 kB gzipped in one, 153 kB in the other. That is demo scaffolding, not the
framework, and it is broken out separately on the stacks page for exactly that
reason.

What the numbers are good for is the shape of the thing: an island-based content
site ships no JavaScript at all on a page of prose, a compiled framework ships
tens of kilobytes, and a framework with a router, a query cache and a table
library ships hundreds. That ranking is stable across any honest way of
measuring it, and it is worth knowing before you pick.
